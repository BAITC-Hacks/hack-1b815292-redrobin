# Техническое задание на прототип анализа организационной структуры и функционала

Статус документа: готово к разработке прототипа

Дата: 23 сентября 2026 года

Основной вывод: за пять часов команда делает один сквозной сценарий для двух файлов DOCX. Один сервер FastAPI извлекает пункты и структуру документов, вызывает одну модель OpenAI для смысловых задач, проверяет каждую ссылку на источник и показывает только подтвержденные выводы. База данных, очередь задач, векторная база и отдельный frontend в P0 не нужны.

## 1. Краткое решение

Прототип помогает сотруднику, который проверяет документы до и после реорганизации. Пользователь загружает две редакции положения. Приложение извлекает разделы, пункты, подразделения, роли и функции. Затем оно сопоставляет старые и новые элементы, отделяет редакционные правки от изменений смысла и формирует список изменений.

Основной демонстрационный набор состоит из редакций 8 и 9 Положения о внутреннем аудите. Пользователь видит созданные и сохраненные подразделения, изменения должностей, новые направления аудита и изменения обязанностей. Каждый вывод открывается в интерфейсе и содержит точные цитаты, номера пунктов и названия документов.

Прототип не принимает кадровые, юридические или управленческие решения. Потеря функции, дублирование и конфликт интересов считаются потенциальными рисками. Приложение включает их в отчет только после проверки источников и помечает для ручной проверки. Если источников недостаточно, результатом становится "Недостаточно данных для вывода".

Ограничения P0:

- приложение принимает ровно два файла DOCX;
- один процесс сервера обрабатывает не более одного анализа одновременно;
- файлы и результаты хранятся временно;
- модель получает только нужные пункты, а не выполняет поиск по внешним источникам;
- PDF, Excel, OCR, постоянное хранение и авторизация не входят в основной сценарий.

### 2.2. Принятые решения

| ID | Решение | Причина | Последствие |
| --- | --- | --- | --- |
| D-1 | Один сервис FastAPI с Jinja2 и небольшим JavaScript | Снижает время сборки и деплоя | Нет отдельного frontend проекта и отдельного API сервера |
| D-2 | Детерминированный парсер выполняется до AI | Он надежно сохраняет текст и координаты источника | Модель не придумывает номера пунктов и цитаты |
| D-3 | Пункты являются основной единицей обработки | Документы используют нумерованные пункты и подпункты | Разбиение по числу символов запрещено |
| D-4 | Одна модель OpenAI используется для всех смысловых шагов | Меньше настроек и меньше риск интеграции | Модель задается через `OPENAI_MODEL` |
| D-5 | Используется Responses API и Structured Outputs | Строгая JSON схема снижает число ошибок формата | Каждый AI ответ проходит Pydantic проверку |
| D-6 | Модель выбирает идентификаторы источников, а цитаты подставляет сервер | Модель не должна переписывать цитату | Точная цитата всегда берется из сохраненного `Clause.raw_text` |
| D-7 | Отчет собирается детерминированно | Итог не должен содержать новый неподтвержденный вывод | AI может написать только краткое резюме по списку проверенных ID |
| D-8 | В P0 нет базы данных и очереди | Для одной демонстрации достаточно памяти процесса и временных файлов | Один worker, потеря заданий после перезапуска допустима |
| D-9 | NVIDIA не используется в P0 | Нет подтвержденного преимущества на контрольных примерах | Сравнение возможно только после готовности P0 |
| D-10 | Для результатов используются термины "подтверждено документом", "потенциальный риск" и "недостаточно данных" | Термины отделяют факт от рекомендации | Интерфейс не показывает риск как установленное нарушение |

Официальная документация OpenAI рекомендует Structured Outputs вместо обычного JSON mode, когда модель должна соблюдать схему. Техническая реализация использует `text.format` с `json_schema` в Responses API. Ссылка для README: <https://developers.openai.com/api/docs/guides/structured-outputs>.

## 3. Границы проекта

### 3.1. P0

P0 должен быть полностью готов за пять часов:

1. Загрузка двух DOCX с явными ролями "до" и "после".
2. Проверка типа, размера, целостности и предполагаемого порядка редакций.
3. Извлечение исходных абзацев, заголовков, пунктов и подпунктов с сохранением точного текста.
4. Извлечение подразделений, ролей, функций, прав и обязанностей в JSON.
5. Сопоставление структуры и функций, включая изменение номера пункта.
6. Классификация двенадцати типов результата, заданных в кейсе.
7. Поиск кандидатов на потерю, дублирование и конфликт интересов.
8. Проверка каждого доказательства по исходному DOCX.
9. Итоговый HTML отчет с фильтрами и раскрываемыми цитатами.
10. JSON API, тесты контрольного набора, Dockerfile и README.

### 3.2. P1

P1 выполняется только после приемки P0:

- загрузка PDF с текстовым слоем;
- загрузка Excel с одной структурированной таблицей;
- выгрузка отчета в DOCX или PDF;
- изменение статуса ручной проверки и экспорт комментария проверяющего;
- короткое сравнение OpenAI и NVIDIA на пяти контрольных примерах;
- хранение нескольких анализов между перезапусками;
- поддержка внешних нормативных документов;
- сравнение с открытыми данными других операторов.

### 3.3. Не входит в решение

В прототип не входят OCR, обучение собственной модели, fine tuning, векторная база, автономный агент с инструментами, очередь задач, микросервисы, SSO, роли доступа, промышленное журналирование, юридически значимое заключение и автоматическое изменение организационной структуры.

## 4. Пользовательский сценарий

### 4.1. Основной путь

1. Пользователь открывает страницу загрузки. Интерфейс показывает два поля: "Редакция до" и "Редакция после".
2. Пользователь выбирает два DOCX. Интерфейс показывает имя, размер и результат первичной проверки каждого файла.
3. Сервер читает заголовок и номер редакции. Если порядок похож на обратный, интерфейс просит подтвердить порядок или поменять файлы местами.
4. Пользователь запускает анализ. Кнопка блокируется, а страница показывает текущий этап и число обработанных пунктов.
5. Сервер извлекает пункты, структуру и функции. Затем он сопоставляет элементы и проверяет доказательства.
6. После завершения пользователь видит краткое заключение, счетчики типов изменений и список выводов.
7. Пользователь открывает вывод. Карточка показывает цитату из редакции 8, цитату из редакции 9, номера пунктов, обоснование, уверенность и статус ручной проверки.
8. Пользователь фильтрует выводы по типу и значимости. Потенциальные риски визуально отделены от подтвержденных структурных изменений.

### 4.2. Состояния интерфейса

| Состояние | Что видит пользователь | Доступное действие |
| --- | --- | --- |
| `empty` | Два пустых поля загрузки | Выбрать файлы |
| `validating` | Проверка формата и размера | Дождаться результата или отменить выбор |
| `ready` | Имена файлов, роли и предупреждения о порядке | Запустить анализ или поменять файлы |
| `extracting` | Этап "Извлекаем разделы и пункты" | Смотреть прогресс |
| `analyzing` | Этапы извлечения сущностей, сопоставления и классификации | Смотреть прогресс |
| `verifying` | Этап "Проверяем цитаты и источники" | Смотреть прогресс |
| `completed` | Заключение и проверенные выводы | Открывать, фильтровать и повторить анализ |
| `completed_with_warnings` | Результат и список отброшенных неподтвержденных кандидатов без их содержания в заключении | Проверить предупреждения |
| `failed` | Понятная причина и сохраненные входные файлы в пределах TTL | Повторить этап или загрузить файлы заново |

### 4.3. Ошибки пользователя

Неподдерживаемый формат, слишком большой файл, поврежденный DOCX и один файл вместо двух блокируют запуск. Ошибка показывает причину рядом с нужным файлом. Введенные данные не очищаются.

## 5. Формат результата

Каждый вывод хранится как объект `Finding`.

| Поле | Тип | Правило |
| --- | --- | --- |
| `id` | string UUID | Уникальный идентификатор вывода |
| `change_type` | enum | Один из двенадцати классов раздела 5.1 |
| `match_id` | string or null | Ссылка на сопоставление, которое связывает старую и новую формулировку |
| `semantic_relation` | enum | `equivalent`, `broader`, `narrower`, `different`, `not_applicable` |
| `subject` | object | Подразделение, роль или функция. Содержит `kind`, `name` и ссылки на сущности |
| `description` | string | Одно проверяемое утверждение без новых фактов |
| `severity` | enum | `info`, `low`, `medium`, `high` |
| `confidence` | number | Значение от 0 до 1. Значение не заменяет доказательство |
| `before_evidence` | array of Evidence | Источники из редакции 8 |
| `after_evidence` | array of Evidence | Источники из редакции 9 |
| `clause_numbers` | array of string | Номера пунктов из обеих редакций |
| `rationale` | string | Почему источники подтверждают тип изменения |
| `manual_review_status` | enum | `not_required`, `pending`, `confirmed`, `rejected` |
| `validation_status` | enum | `verified`, `insufficient`, `rejected` |
| `recommendation` | string or null | Только действие для ручной проверки, без категоричного решения |

### 5.1. Допустимые классы

1. `unit_preserved`, подразделение сохранено.
2. `unit_created`, подразделение создано.
3. `unit_removed`, подразделение упразднено.
4. `unit_transformed`, подразделение преобразовано.
5. `function_preserved`, функция сохранена без изменения смысла.
6. `function_added`, функция добавлена.
7. `function_missing`, функция удалена или не найдена в новой редакции.
8. `function_moved`, функция перенесена между подразделениями или ролями.
9. `wording_changed`, формулировка изменена, но смысл сохранен.
10. `possible_duplicate`, функция потенциально дублируется.
11. `possible_conflict`, обнаружен потенциальный конфликт интересов.
12. `insufficient_evidence`, данных недостаточно.

Отдельного класса "смысл изменен" в заданном перечне нет. Поэтому изменение смысла хранится в `semantic_relation`. Если новая формулировка расширяет обязанность, создается `function_added` для добавленной части. Если часть старой обязанности исчезает, создается `function_missing` для исчезнувшей части. Оба вывода ссылаются на один `match_id` и показываются в интерфейсе одной группой "Изменение смысла". Такое представление не смешивает смысловую правку с `wording_changed`, который допускается только при сохранении смысла.

### 5.2. Формат доказательства

```json
{
  "id": "ev-uuid",
  "document_id": "doc-before",
  "document_role": "before",
  "document_name": "Положение_..._редакция_8_обезличено.docx",
  "section_title": "3. Структура и организация работы внутреннего аудита",
  "clause_number": "3.4.a",
  "clause_id": "doc-before:p103:0",
  "quote": "а. Департамент непрерывного мониторинга системы внутреннего контроля (ДНМ).",
  "quote_start": 0,
  "quote_end": 78,
  "evidence_type": "presence",
  "validated": true
}
```

Для вывода об отсутствии допускается `evidence_type: "absence_check"`. Такой объект содержит область поиска, поисковый запрос и число найденных кандидатов. Поле `quote` тогда равно `null`. Один объект отсутствия не подтверждает потерю функции. Нужна исходная положительная цитата, полный поиск по документу после реорганизации и статус ручной проверки `pending`.

### 5.3. Правила значимости

- `info` используется для сохранения и редакционной правки.
- `low` используется для локального изменения формулировки без явного влияния на обязанность.
- `medium` используется для новой, перенесенной или не найденной функции.
- `high` допускается только для подтвержденного документами потенциального конфликта, возможной потери существенной функции или широкого дублирования. Статус ручной проверки остается `pending`.

| FR-9 | Различить смысловое и редакционное изменение | P0 | C-08 to C-15 | Редакционные правки не попадают в список добавленных или удаленных функций |
| FR-10 | Создать кандидата на потерю только после поиска по всему документу после | P0 | Негативный тест C-17 | Система возвращает `insufficient_evidence`, если однозначного соответствия нет |
| FR-11 | Найти кандидатов на дублирование с учетом иерархии и исполнителя | P0 | C-18 и синтетический подтвержденный пример | Наследование функции уровня БВА не считается дублированием автоматически |
| FR-12 | Найти явно описанный или обоснованный потенциальный конфликт интересов | P0 | C-10 | Вывод содержит обе стороны конфликта, цитаты и рекомендацию ручной проверки |
| FR-13 | Проверить существование каждого документа, пункта и точной цитаты | P0 | Подмена одного символа в цитате | Неподтвержденный вывод получает `rejected` и исключается из заключения |
| FR-14 | Сформировать отчет только из проверенных выводов | P0 | Интеграционный тест отчета | Все ID в заключении ссылаются на `Finding.validation_status=verified` |
| FR-15 | Показать выводы и источники в серверном HTML интерфейсе | P0 | Ручной сценарий в браузере | Пользователь раскрывает карточку и видит обе редакции рядом |
| FR-16 | Показать этап, прогресс, предупреждения и ошибку | P0 | Тест отказа AI API и поврежденного файла | Пользователь понимает причину и может повторить анализ |
| FR-17 | Вернуть результат через JSON API | P0 | Контрактные тесты API | Ответ соответствует Pydantic схеме и примерам раздела 10 |
| FR-18 | Корректно обработать одинаковые документы | P0 | Загрузка одного файла в обе роли | Отчет сообщает об отсутствии подтвержденных изменений и не создает риски |
| FR-19 | Повторно запустить анализ без повторной загрузки в пределах TTL | P0 | Повторный `POST /analyze` | Производные результаты очищены, а исходные файлы используются повторно |
| FR-20 | Поддержать PDF и Excel | P1 | Отдельные fixtures | Не влияет на приемку P0 |

## 7. Нефункциональные требования

### 7.1. Производительность

- Для двух контрольных DOCX по 25 страниц целевое время от запуска до результата составляет не более 180 секунд при доступном AI API.
- Жесткий тайм-аут одного анализа составляет 300 секунд.
- Парсинг двух контрольных файлов без AI должен занимать не более 10 секунд на машине с двумя CPU и 2 ГБ памяти.
- Одновременно выполняется один анализ. Второй запрос получает `409 analysis_busy`, а не скрытую очередь.

### 7.2. Ограничения файлов

- Максимальный размер одного файла составляет 20 МБ.
- Максимальный суммарный размер распакованных частей DOCX составляет 100 МБ.
- Максимальное число ZIP записей составляет 2000.
- Разрешен только `.docx`. Файлы `.docm`, внешние ссылки и вложенные объекты не выполняются.

### 7.3. Секреты и данные

- `OPENAI_API_KEY` хранится только в переменной окружения и не передается браузеру.
- Содержимое документов, цитаты и ответы модели не записываются в обычный application log.
- Лог содержит `job_id`, длительность этапа, число пунктов, число вызовов и код ошибки.
- Временные каталоги удаляются через 60 минут и при штатном завершении приложения.
- Имя загруженного файла очищается. Путь строится сервером и не использует пользовательский ввод.

### 7.4. Надежность и повторный запуск

- Каждый этап пишет атомарный JSON артефакт во временный каталог задания.
- Повторный запуск использует уже проверенный результат парсинга, если хеш файла не изменился.
- Один сетевой сбой не удаляет файлы и извлеченные пункты.
- После перезапуска сервера незавершенные задания теряются. Интерфейс прямо сообщает об ограничении P0.

### 7.5. Работа после деплоя

- Приложение запускается одной командой в Docker и использует один Uvicorn worker.
- `GET /health` не вызывает AI API и возвращает состояние процесса.
- `GET /ready` проверяет наличие каталогов и обязательных переменных, но не раскрывает секреты.
- Публичная версия не обещает конфиденциальность промышленного уровня. На экране загрузки есть предупреждение использовать только обезличенные материалы.

### 7.6. Обработка ошибок

Все ошибки имеют стабильный код, понятное сообщение и `request_id`. Ответ AI, который не прошел схему, не показывается пользователю как результат. Отказ одного вывода не должен скрывать другие проверенные выводы, если этап может завершиться с предупреждениями.

## 8. Архитектура

### 8.1. Компоненты

```text
Браузер
  -> FastAPI и Jinja2
      -> Job service и временное хранилище
      -> DOCX parser и normalizer
      -> Entity extractor
      -> Deterministic matcher
      -> OpenAI semantic analyzer
      -> Evidence validator
      -> Report builder
```

FastAPI принимает файлы и отдает HTML и JSON. `Job service` хранит состояние в словаре процесса и создает временный каталог. Парсер работает только с документами. AI слой получает нормализованные пункты с идентификаторами. Валидатор снова обращается к исходным данным и не доверяет тексту модели. `Report builder` принимает только проверенные `Finding`.

### 8.2. Поток данных

1. `UploadService` сохраняет два файла, считает SHA-256 и проверяет DOCX.
2. `DocxParser` читает OOXML, абзацы, стили и сведения о нумерации.
3. `ClauseSegmenter` формирует разделы и логические пункты. Каждый фрагмент хранит диапазон внутри исходного абзаца.
4. `EntityExtractor` находит кандидатов по правилам и уточняет их через AI.
5. `Matcher` сначала сопоставляет номера и близкие тексты, затем передает неоднозначные случаи AI.
6. `RiskAnalyzer` строит только кандидатов потери, дублирования и конфликта.
7. `EvidenceValidator` проверяет идентификаторы, пункты и точные подстроки.
8. `ReportBuilder` создает JSON и HTML результат из прошедших проверку объектов.

### 8.3. Рекомендуемый стек

| Область | Выбор |
| --- | --- |
| Язык | Python 3.12 |
| Сервер | FastAPI, Uvicorn |

| DOCX | `python-docx` и стандартный `zipfile` для недоступных через библиотеку свойств OOXML |
| Модели | Pydantic v2 |

Поэтому `.env` требует явное значение `OPENAI_MODEL`, а smoke test проверяет вызов до начала основной разработки. Приложение не должно содержать зашитое имя модели.

## 10. API

Все JSON ошибки используют формат:

```json
{
  "error": {
    "code": "invalid_docx",
    "message": "Файл редакции до поврежден или не является DOCX.",
    "field": "before_file",
    "request_id": "req-uuid",
    "retryable": false
  }
}
```

### 10.1. Загрузка

`POST /api/jobs`

Запрос `multipart/form-data`:

- `before_file`: обязательный DOCX;
- `after_file`: обязательный DOCX.

Успешный ответ `201 Created`:

```json
{
  "job_id": "job-uuid",
  "status": "ready",
  "documents": [
    {"role": "before", "name": "...редакция_8....docx", "revision_label": "8"},
    {"role": "after", "name": "...редакция_9....docx", "revision_label": "9"}
  ],
  "warnings": []
}
```

Ошибки: `400 missing_file`, `413 file_too_large`, `415 unsupported_media_type`, `422 invalid_docx`.

### 10.2. Запуск анализа

`POST /api/jobs/{job_id}/analyze`

Запрос:

```json
{
  "confirm_order": false,
  "force_restart": false
}
```

Ответ `202 Accepted`:

```json
{
  "job_id": "job-uuid",
  "status": "extracting",
  "stage": "parse_documents",
  "progress": 0.05
}
```

Ошибки: `404 job_not_found`, `409 order_confirmation_required`, `409 analysis_busy`, `409 already_running`, `422 invalid_state`.

### 10.3. Получение статуса

`GET /api/jobs/{job_id}`

Ответ `200 OK`:

```json
{
  "job_id": "job-uuid",
  "status": "analyzing",
  "stage": "match_functions",
  "progress": 0.62,
  "started_at": "2026-09-23T10:00:00Z",
  "updated_at": "2026-09-23T10:01:12Z",
  "warnings": [],
  "error": null
}
```

Ошибки: `404 job_not_found`. Статусы: `ready`, `extracting`, `analyzing`, `verifying`, `completed`, `completed_with_warnings`, `failed`.

### 10.4. Получение результата

`GET /api/jobs/{job_id}/result`

Ответ `200 OK` содержит `Report` из раздела 9.10. `GET /jobs/{job_id}` возвращает серверный HTML с теми же данными.

Ошибки: `404 job_not_found`, `409 result_not_ready`, `410 job_expired`.

### 10.5. Повторный запуск

Повторный `POST /api/jobs/{job_id}/analyze` с `force_restart=true` очищает производные данные и сохраняет проверенные входные файлы. Запрос доступен только до истечения TTL.

## 11. AI конвейер

### 11.1. Общие настройки

- Провайдер: OpenAI.
- API: Responses API.
- Модель: значение `OPENAI_MODEL`, проверенное smoke test.
- Формат: Structured Outputs с `strict: true` и `additionalProperties: false`.
- Reasoning effort: `low`, если модель поддерживает параметр. Иначе параметр не передается.
- Temperature: `0`, если модель поддерживает параметр. Иначе параметр не передается.
- Сетевой тайм-аут одного вызова: 60 секунд.
- Вход разбивается по разделам и связанным пунктам, а не по числу символов.
- Документ считается недоверенными данными. Инструкции внутри документа не выполняются.

Для `429`, `500`, `502`, `503`, `504` выполняются две повторные попытки с задержкой 2 и 4 секунды. Для ошибки схемы выполняется одна корректирующая попытка. Отказ модели, фильтр безопасности или повторная ошибка схемы останавливают текущий AI этап. Парсинг и уже проверенные данные сохраняются.

### 11.2. Шаг AI-1 Извлечение сущностей

Вход: один раздел, список `Clause` с ID, список детерминированно найденных названий и известный заголовок раздела.

Выход: подразделения, роли и функции. Модель может ссылаться только на переданные `clause_id`.

```json
{
  "units": [
    {
      "name": "string",
      "short_name": "string|null",
      "unit_type": "block|department|center|other",
      "parent_name": "string|null",
      "source_clause_ids": ["string"],
      "confidence": 0.0
    }
  ],
  "roles": [
    {
      "name": "string",
      "unit_name": "string|null",
      "reports_to": "string|null",
      "source_clause_ids": ["string"],
      "confidence": 0.0
    }
  ],
  "functions": [
    {
      "actor_name": "string",
      "actor_type": "unit|role|block",
      "kind": "task|function|right|duty|restriction",
      "canonical_text": "string",
      "source_clause_ids": ["string"],
      "confidence": 0.0
    }
  ]
}
```

Условие отказа: неизвестный `clause_id`, пустой источник, уверенность вне диапазона или повторная ошибка схемы. Неизвестная сущность не добавляется.

### 11.3. Шаг AI-2 Смысловое сопоставление

Вход: один элемент до, не более пяти кандидатов после, их функции и точные пункты. Кандидаты заранее отобраны по номеру, разделу, названию и текстовому сходству.

Выход:

```json
{
  "matches": [
    {
      "before_id": "string",
      "after_id": "string|null",
      "relation": "equivalent|renamed|narrower|broader|moved|different|no_match|uncertain",
      "before_clause_ids": ["string"],
      "after_clause_ids": ["string"],
      "confidence": 0.0,
      "rationale": "string"
    }
  ]
}
```

Условие отказа: модель выбирает ID вне списка, не приводит источник с обеих сторон для пары или возвращает `no_match` без просмотра всех переданных кандидатов. Такой объект становится `uncertain`.

### 11.4. Шаг AI-3 Классификация изменения

Вход: проверенная пара или непарный элемент, сведения об исполнителе и связанные пункты.

Выход:

```json
{
  "findings": [
    {
      "draft_id": "string",
      "match_id": "string|null",
      "change_type": "unit_preserved|unit_created|unit_removed|unit_transformed|function_preserved|function_added|function_missing|function_moved|wording_changed|possible_duplicate|possible_conflict|insufficient_evidence",
      "semantic_relation": "equivalent|broader|narrower|different|not_applicable",
      "subject_refs": ["string"],
      "before_clause_ids": ["string"],
      "after_clause_ids": ["string"],
      "severity": "info|low|medium|high",
      "confidence": 0.0,
      "rationale": "string",
      "manual_review_required": true
    }
  ]
}
```

Условие отказа: `function_missing`, `possible_duplicate` или `possible_conflict` без источника и объяснения. Такой объект заменяется на `insufficient_evidence` или удаляется.

### 11.5. Шаг AI-4 Анализ возможного дублирования и конфликта

Вход: пары функций разных исполнителей, их место в иерархии, ограничения, права и обязанности. Общая функция блока и ее детализация у подчиненной роли не считаются дублированием по умолчанию.

Выход:

```json
{
  "risks": [
    {
      "risk_type": "possible_duplicate|possible_conflict|insufficient_evidence",
      "subject_refs": ["string"],
      "clause_ids": ["string"],
      "overlap": "string",
      "why_it_may_matter": "string",
      "counter_evidence_clause_ids": ["string"],
      "confidence": 0.0,
      "manual_check": "string"
    }
  ]
}
```

Условие отказа: одна сторона риска не имеет цитаты, иерархическая связь не рассмотрена или модель повторяет слово "дублирующий" из текста как доказательство фактического дублирования.

### 11.6. Шаг AI-5 Проверка достаточности доказательств

Вход: один черновик `Deviation`, исходные пункты и найденное контрдоказательство.

Выход:

```json
{
  "decisions": [
    {
      "draft_id": "string",
      "verdict": "supported|unsupported|insufficient",
      "supporting_clause_ids": ["string"],
      "contradicting_clause_ids": ["string"],
      "reason": "string"
    }
  ]
}
```

Результат AI-5 не является окончательной проверкой. После него детерминированный валидатор проверяет все ID и цитаты. `unsupported` удаляется. `insufficient` отображается только как воздержание от вывода.

### 11.7. Шаг AI-6 Краткое заключение

Вход: только проверенные `Finding`, их ID и разрешенные формулировки.

Выход:

```json
{
  "summary": "string",
  "key_finding_ids": ["string"],
  "recommendations": [
    {
      "text": "string",
      "based_on_finding_ids": ["string"]
    }
  ]
}
```

Условие отказа: неизвестный `finding_id`, число или факт, которого нет в проверенных данных, либо категоричная рекомендация по потенциальному риску. При ошибке сервер создает шаблонное заключение без AI.

## 12. Защита от выдуманных выводов

Каждый вывод проходит обязательные проверки в следующем порядке:

1. `document_id` должен принадлежать текущему заданию и правильной роли документа.
2. `clause_id` должен существовать в результате парсинга этого документа.
3. Номер пункта берется из `Clause.number`, а не из ответа модели.
4. Цитата берется из `Clause.raw_text` по сохраненному диапазону.
5. После нормализации только пробелов цитата должна оставаться точной подстрокой исходного абзаца.
6. Тип изменения должен допускать требуемые источники. Например, `unit_preserved` требует источники с обеих сторон.
7. Вывод о потере требует старую положительную цитату, полный поиск по новой редакции и отсутствие сильного кандидата.
8. Вывод о дублировании требует минимум две функции, двух исполнителей и проверку иерархического наследования.
9. Вывод о конфликте требует две несовместимые обязанности или прямое описание конфликта в документе.
10. Заключение может ссылаться только на `Finding.validation_status=verified`.

Если проверка 1 to 5 не проходит, черновик получает `rejected` и не показывается как вывод. Если проверки 6 to 9 не дают достаточного основания, система создает `insufficient_evidence` с объяснением. Значение `confidence` никогда не обходит эти правила.

Инструкции, найденные внутри загруженного документа, считаются обычным текстом. Модель не имеет инструментов, не обращается к URL из документа и не получает секреты приложения.

| Хранилище | Задание старше 60 минут | `410 job_expired` и файлы удалены | P0 | Создать новое задание |
| Безопасность | В тексте есть инструкция модели | Инструкция остается данными и не выполняется | P0 | Вывод без особого действия пользователя |

Пользовательские сообщения:

| Код | Сообщение | Действие |
| --- | --- | --- |
| `invalid_docx` | "Файл поврежден или не является DOCX." | "Выбрать другой файл" |

## 16. Критерии приемки

Контекст: P0 сравнивает два DOCX и показывает только выводы с проверяемыми источниками.

### AC-01 Успешный анализ контрольных документов

Given пользователь загрузил оригинальную редакцию 8 как документ до и редакцию 9 как документ после

When пользователь запускает анализ

Then приложение завершает задание, показывает ДИТААД и ДОА как созданные, ДНМ и ДККМ как сохраненные и дает раскрыть точные источники для каждого вывода

### AC-02 Просмотр доказательств

Given отчет содержит проверенный вывод

When пользователь открывает карточку вывода

Then интерфейс показывает название документа, номер пункта, точную цитату, обоснование, уверенность и статус ручной проверки

### AC-03 Редакционное изменение

Given документы содержат изменение из C-13, C-14 или C-15

When приложение классифицирует пару пунктов

Then результат имеет класс `wording_changed` и не создает добавленную или потерянную функцию

### AC-04 Смысловое изменение одного слова

Given документы содержат пункты 9.15 из C-11

When приложение сопоставляет пункты

Then результат сообщает об изменении модальности и показывает слово "может" в источнике редакции 9

### AC-05 Перенумерованная функция

Given одна функция находится в пункте 5.5.5 редакции 8 и в пункте 5.5.3 редакции 9

When приложение сопоставляет функции

Then функция не считается новой только из-за изменения номера

### AC-06 Недостаточно подтверждения

Given модель предлагает вывод и хотя бы одна его цитата отсутствует в исходном пункте

When детерминированный валидатор проверяет доказательства

Then вывод получает статус `rejected`, не входит в заключение и увеличивает счетчик отброшенных кандидатов

### AC-07 Воздержание от вывода о потере

Given старая роль не имеет однозначной пары, но ее обязанности встречаются у нескольких новых ролей

When приложение завершает сопоставление

Then результат имеет класс `insufficient_evidence`, а приложение не утверждает потерю функции

### AC-08 Потенциальный конфликт

Given пункт 4.4 редакции 9 прямо описывает потенциальный конфликт при совмещении

When приложение формирует риск

Then риск помечен как потенциальный, имеет статус ручной проверки `pending` и не утверждает, что конфликт реализовался

### AC-09 Ошибка AI API

Given документы успешно разобраны, а AI API возвращает ошибку после допустимых повторов

When выполняется смысловой этап

Then задание переходит в `failed`, интерфейс показывает `ai_unavailable`, исходные файлы и результат парсинга сохраняются до TTL, а пользователь может повторить анализ

### AC-10 Поврежденный файл

Given пользователь выбрал файл с расширением `.docx`, который не содержит обязательных частей OOXML

When сервер проверяет загрузку

Then сервер возвращает `422 invalid_docx`, не вызывает AI и сохраняет второй выбранный файл в форме браузера

### AC-11 Одинаковые документы

Given оба файла имеют одинаковый SHA-256

When пользователь подтверждает анализ

Then приложение формирует отчет без изменений и не создает риски потери, дублирования или конфликта

### AC-12 Обратный порядок

Given номер редакции документа до больше номера редакции документа после

When пользователь запускает анализ без подтверждения

Then сервер возвращает `409 order_confirmation_required` и не начинает AI вызовы

### AC-13 Время обработки

Given сервер имеет два CPU, 2 ГБ памяти и доступный AI API

When анализируются две контрольные редакции по 25 страниц

Then результат готов не позднее 180 секунд, а при достижении 300 секунд задание завершается контролируемой ошибкой тайм-аута

### AC-14 Безопасность ключа

Given приложение развернуто с `OPENAI_API_KEY`

When пользователь открывает HTML, API ответы и логи обычного уровня

Then значение ключа и заголовок авторизации отсутствуют во всех ответах и логах

### AC-15 Повторный запуск

Given неуспешное или завершенное задание еще не истекло

When пользователь запускает повторный анализ

Then сервер использует те же проверенные файлы, очищает старые производные результаты и создает новый результат без смешивания версий

### AC-16 Склеенные пункты

Given исходный абзац содержит пункты 3.9, 3.10 и 3.11 редакции 8

When парсер создает логические пункты

Then каждый номер имеет отдельный `Clause.id`, а каждая цитата точно восстанавливается по диапазону исходного абзаца

### AC-17 Иерархическое повторение функции

Given функция БВА из пункта 2.4.17.б повторяется в обязанностях руководящих ролей в пункте 5.3.3.б

When приложение проверяет возможное дублирование

Then приложение учитывает связь блока и ролей, не публикует подтвержденное дублирование и объясняет недостаточность основания

### AC-18 Подтвержденное дублирование в тестовом fixture

Given синтетический fixture содержит одинаковую исключительную ответственность у двух независимых подразделений и точные источники с обеих сторон

When приложение выполняет анализ рисков

Then приложение создает `possible_duplicate`, показывает обе цитаты и ставит `manual_review_status=pending`

### AC-19 Статус задания

Given анализ выполняется

When клиент запрашивает `GET /api/jobs/{job_id}`

Then API возвращает один из документированных этапов, значение `progress` от 0 до 1 и не возвращает частичный неподтвержденный отчет

### AC-20 Контракт результата

Given анализ завершен

When клиент запрашивает `GET /api/jobs/{job_id}/result`

Then ответ соответствует схеме `Report`, каждый опубликованный `Finding` имеет проверенное доказательство, а неизвестные поля отсутствуют

python -m venv .venv

В `.env.example` не должно быть рабочего ключа. README должен отдельно сказать, что доступность модели зависит от выданного ключа, а имя модели проверяется smoke test.

## 20. Риски и решения

| Риск | Вероятность | Ущерб | Ранний признак | Действие команды |
